# 요약 - 진짜 AI 네이티브 조직을 현실적으로 구축하는 법

## 한 줄 요약
Jeongmin Lee의 LinkedIn 글은 기업 AX를 “AI 도구 도입”이 아니라 조직 운영체계의 재설계로 보고, skill, resolver, filing rules, check-resolvable, trigger eval을 각각 직원, 조직도, 내부 프로세스, 감사/컴플라이언스, 인사 평가에 대응시키는 실무 프레임을 제안한다.

## 핵심 내용
- **문제 배경:** 작성자는 사업자 등록 후 20영업일 동안 AX 협업 문의가 이어졌고, 금융권을 포함한 다양한 조직에서 AI 네이티브 전환 수요가 있었다고 설명한다.
- **두 가지 출발점:** 이미 굴러가는 조직을 AI 네이티브하게 바꾸려면 기존 문서/시스템을 AI가 읽을 수 있는 자산으로 만들거나, AI 사용 문화를 시작해야 한다고 본다.
- **Skill = 직원:** 직원 한 명이 특정 능력을 갖듯, skill 하나가 반복 작업 하나를 수행한다. 조직 공통 skill과 직원별 인터뷰 기반 skill을 구축할 수 있다.
- **Resolver = 조직도:** 모든 지시를 `CLAUDE.md` 같은 단일 파일에 넣지 않고, 필요할 때 담당 파일/skill을 불러오도록 escalation/라우팅 규칙을 둔다.
- **Filing rules = 내부 프로세스:** 파일명, 폴더, 업로드 이벤트, read-only AI 파일이 조직의 일하는 방식이 된다. 기존 데이터를 갈아엎기보다 AI가 읽을 수 있는 정보 자산화 시스템을 만든다.
- **Check-resolvable = 감사/컴플라이언스:** skill 중복, 누락, 실제 작동 여부를 점검한다. DRY/MECE, unit test, LLM eval 같은 검증 계층이 핵심이다.
- **Trigger eval = 인사 평가:** 실제 요청이 들어왔을 때 resolver가 올바른 skill을 호출했는지, skill 결과가 기대 품질을 냈는지 평가한다. 아직은 도메인 판단과 커뮤니케이션 품질에서 인간의 역할이 크다.
- **구축 순서:** 기존 데이터 유지 -> 파일명/파일 시스템 정리 -> pointer 기반 지시 파일 -> 반복 작업 skillify -> DB/주요 작업을 tool 및 기업 전용 MCP 서버로 연결 -> 결과 확인용 프롬프트 템플릿과 대시보드.

## 재사용 시 주의
- 이 글은 YC AI Playbook과 Stanford CS153 강연을 바탕으로 한 한국어 실무 해석이다. 원 강연의 표현과 작성자의 구현 계획을 분리해 인용해야 한다.
- “스프린트 절반”, “산출량 10배”, “수천 건 대화를 skill로 압축” 같은 사례는 referenced talks/transcripts의 주장으로 보존했지만, 독립 감사된 수치로 취급하면 안 된다.
- 특히 금융/규제 조직에 적용할 때는 권한, 개인정보, 감사 로그, human-in-the-loop 승인, 모델 출력 책임 소재를 별도 설계해야 한다.
